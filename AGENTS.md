# Рабочий контракт

Этот репозиторий — учебная и переиспользуемая кодовая база на Laravel. Блог как предметная область появится позже; текущий приоритет — базовая система и административная часть.

## Разделение ответственности

Владелец определяет:

- что должно существовать и зачем;
- архитектуру, канон и ограничения;
- границы компонентов;
- появление сущностей и абстракций;
- изменение существующих правил;
- критерий готовности.

Агент:

- сначала исследует существующий проект и Git;
- ищет и переиспользует существующие решения;
- выбирает минимальный путь внутри решений владельца;
- реализует, интегрирует и проверяет согласованное изменение;
- сообщает о проблемах и противоречиях.

Агент не принимает архитектурные решения вместо владельца. Если задача требует новой сущности, абстракции, слоя, паттерна, структурного файла или компонента, второго способа решать существующую задачу либо изменения канона, работа останавливается до решения владельца.

Если существующая архитектура мешает задаче, нельзя обходить её или строить параллельную архитектуру. Проблема возвращается владельцу.

## Зафиксированный канон

- Laravel 13, Inertia 3, Vue 3 Composition API и TypeScript.
- shadcn-vue, Tailwind CSS и Vite.
- Окружение разработки — официальный Laravel Sail.
- PHP, Composer, Node.js, npm и MySQL запускаются в Docker, а не на хосте.
- Единственная база данных — MySQL в отдельном контейнере. SQLite не используется.
- Все связи между будущими доменными сущностями имеют тип многие ко многим, пока владелец явно не изменит это правило.
- Сначала строится системная и административная основа. Предметная часть блога отложена.
- PHP-код обязательно организуется слоями `app/n0_World`, `app/n1_Infra`, `app/n2_System` и будущими предметными слоями `app/n3_*` и выше.
- `n0_World` содержит независимые фундаментальные понятия, `n1_Infra` — инфраструктуру приложения, `n2_System` — пользователей, доступ, админку, виджеты и другие системные возможности.
- Новые предметные слои `n3_*` и выше появляются только по решению владельца.
- `/home/zephyr/dev/business-os` — проект-референс. Решения из него можно переносить только после проверки применимости и явного решения владельца.

## Как выполнять работу

- Перед изменением искать существующий способ сделать требуемое.
- Не добавлять сущности, поля, зависимости и универсальные механизмы «на будущее».
- Использовать Sail и рецепты `justfile`; не вводить параллельные команды окружения.
- Тяжёлые команды (`docker pull/build/up`, установка зависимостей, миграции и полные проверки) отдавать владельцу с точной командой. Самостоятельно запускать их только по прямому поручению.
- После frontend-изменений проверять форматирование, типы и production build.
- После backend-изменений запускать относящиеся к задаче тесты, затем полный набор проверок, если состояние проекта это позволяет.
- Не коммитить и не отправлять изменения без прямой команды владельца.
- Не включать `.env`, секреты, зависимости и runtime-файлы в Git.

## Перед началом задачи

Проверь:

```bash
git status --short
git diff --stat
git diff --cached --stat
```

Рабочее дерево может содержать незавершённые изменения владельца. Их нельзя удалять или перезаписывать.
